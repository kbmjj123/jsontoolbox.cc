# 需求 01：Docker 自托管发布能力

## 优先级与目标

优先级：P0，建议首先实施。为已安装 Docker 的用户提供无需本地编译的 JsonToolBox 实例；这不包含自动安装 Docker、配置域名或提供公网安全保障。

成功标准：用户按文档拉取公开预构建镜像后可以启动实例；核心处理在浏览器进行；官网构建与自托管构建互不破坏。

## 用户场景

- 个人电脑运行独立 JSON 工具。
- 团队在受控内网部署，无须依赖作者官网提供处理服务。
- NAS 用户复用同一镜像，后续由平台模板接入。

## 范围与非目标

包含 Dockerfile、.dockerignore、Compose、发布工作流、部署说明和自托管配置。暂不包含账号系统、数据库、管理后台、多租户、自动升级服务和许可证服务器。自托管默认不提供远程 JSON 存储。

## 架构调查与选型

检查 Nuxt 构建配置、server 路由、分享功能、第三方资源、Worker/WASM 加载路径、国际化和所有主站域名常量。优先验证静态输出是否足够；存在必要服务端依赖时记录替代方案，不能为了容器化直接改坏官网 SSR 或 SEO。

同仓库维护官网与自托管模式。明确两种模式功能差异；自托管关闭广告、主站统计、远程验证与不必要外部请求。必要资源本地提供。不能离线工作的功能需禁用或清楚标识。

## 功能需求

### 镜像与启动

- 多阶段构建；最终运行镜像不包含源码凭据、开发依赖或构建缓存。
- 优先非 root 运行，选定内部监听端口；文档与健康检查同步使用该端口，不预设必须为 80。
- 提供单条 docker run 命令与 Compose；本机示例默认绑定 127.0.0.1，内网访问单独说明。
- 不要求挂载持久化卷才能使用核心工具；若存在浏览器本地状态，说明它不等于容器内持久化。
- 配置资源限额、只读文件系统等加固选项前先验证兼容性，不提供未经测试的安全保证。

### 配置模型

列出每个配置的用途、默认值、应用时机和安全边界。至少评估站点名称、部署基址、品牌展示、索引策略、广告与统计关闭方式。

静态文件不能直接读取容器启动环境变量。若支持运行时配置，应由启动脚本生成白名单配置文件，由应用读取；禁止把任意环境变量或秘密注入前端。若暂不实现，应明确哪些配置只能重新构建。

### 路由、分享与索引

验证首页、工具页、多语言页和不存在页面的直接访问与刷新。静态服务器不得对所有缺失资源无条件返回 HTML，避免掩盖 JS/Worker 404。

分享链接应按明确规则使用当前实例地址；打开官网只由用户主动触发且不得携带 JSON。自托管默认不提供 sitemap 并设置 noindex；如提供允许索引选项，必须要求部署者设置自身基址和 canonical。noindex 不是认证或保密措施。

### 发布与供应链

建议镜像标识 ghcr.io/kbmjj123/jsontoolbox，最终待确认。固定版本标签用于可复现部署，latest 仅作便捷入口。版本发布与主仓库 Release 关联，构建 amd64/arm64 并分别进行运行冒烟测试。CI 使用最小权限，不在日志输出密钥。记录基础镜像更新和漏洞修复流程。

## 验收矩阵

1. 干净环境仅凭 Docker 和文档启动，无须 Node 或源码构建。
2. 核心格式化、校验、树形查看、文件导入与导出可用；其他功能按实际能力列出。
3. 下载镜像后，阻断外网时核心功能仍可运行；检查网络面板并记录例外。
4. 编辑器 Worker、WASM、字体和静态资源加载无 404。
5. 本机默认不向所有接口开放；受控内网模式按说明可访问。
6. 升级固定版本及回滚成功；关闭来源展示不影响工具。
7. 构建产物和浏览器日志中无密钥、无 JSON 原文泄露。

## 文档与来源链接

README 自托管章节及独立部署指南提供在线演示、源码、许可证入口。镜像说明解释在线版和自托管差异，不承诺 SEO 权重或内网实例形成公开外链。

## 风险与退出条件

若必要功能高度依赖主站服务，先缩小自托管功能清单；不得为了快速交付隐藏远程依赖。若多架构尚未验证，不发布对应支持声明。

## 通用实施约束

1. 本文为需求与验收依据，不代表仓库已经具备文中能力。实施前检查实际代码、构建脚本、许可证、组件 API 和发布配置；不得虚构检查结果。
2. 产品名称统一为 JsonToolBox；官网为 https://jsontoolbox.cc/；主仓库为 https://github.com/kbmjj123/jsontoolbox.cc。新增包名、镜像名和仓库名均为待确认建议，发布前检查可用性。
3. 优先复用现有编辑器与处理逻辑，不复制维护第二套核心，不引入与需求无关的账号、数据库、云端处理和许可证验证服务。
4. JSON 内容不得默认上传、写入分析事件或附加在外部链接中；错误日志不得包含用户原文。不要把“本地处理”直接等同于整个页面没有外部请求。
5. 官网、源码和许可链接用于说明来源。不得要求强制反链、指定 dofollow、隐藏链接或堆砌关键词；品牌展示可关闭，不得影响功能。许可证义务以仓库实际许可证为准，不将保留网页反链描述为 MIT 的要求。
6. 新增追踪、外部服务、软件包发布、平台提交和对第三方发起 PR 均需维护者确认。默认不增加遥测。
7. 不为链接数量创建空壳包、重复仓库或无实际用途的适配层。下载、拉取、引用和真实用户分别统计，不混为一谈。
8. 使用项目现有包管理器、测试方案和编码规范；本文示例命名可按仓库结构调整，调整需说明理由。

## 开工前必须输出

- 相关文件、组件入口、构建命令及当前行为的检查记录。
- 已有能力、缺失能力和阻塞项列表；不能确认的内容标记“待核实”。
- 最小变更方案、拟修改文件清单及复用关系。
- 本次验收方式与回归范围。遇到架构或发布权限阻塞时停止猜测，记录需要维护者确认的决策。

- 文档内命令必须在目标环境验证；未执行的测试标为“未验证”，不能直接勾选通过。
- 不影响官网现有工具、现有组件消费者及 Obsidian 插件；相关共享核心发生变更时执行回归。
- 发布前提供变更摘要、涉及外部服务清单和维护成本说明。未获得发布授权时仅交付待发布产物与操作说明。
