# 需求 04：NAS／自托管平台安装模板（首站 Unraid）

## 优先级与前置条件

优先级：P1，必须在 Docker 需求验收后实施。首版只选择一个平台，建议先评估 Unraid；正式实施前核实平台当前提交规则和维护要求。收录不保证，不能把外链作为验收条件。

## 目标与用户场景

让 NAS 用户通过平台模板配置端口并运行已发布的 JsonToolBox 镜像，无需学习前端构建。不重新维护一个特殊版镜像。

## 前置检查

- 官方镜像及固定版本可公开拉取。
- 镜像支持目标设备架构，已有实际运行记录。
- 了解平台模板格式、图标规范、发布渠道、审核及更新方式。
- 有真实目标平台测试环境；没有时只交付草案，不声明已支持。

## 模板需求

依据平台实际格式提供名称、简短描述、分类、镜像、端口、Web UI 地址、图标、项目来源、支持和许可信息。可填写字段按当前规范确定，不虚构平台支持的字段。

默认只提供必要设置；不要求 privileged、Docker socket、主机目录全盘挂载或 host 网络。无持久化需求时不人为添加数据卷。

镜像版本选择与升级行为写清楚。说明平台桥接、局域网访问和本机 Docker 示例的区别，不照搬 127.0.0.1 配置导致 NAS 客户端无法访问。

## 用户文档

- 安装及首次打开。
- 端口冲突与架构不兼容排查。
- 更新、固定版本、回滚与卸载。
- 浏览器状态和容器状态的区别。
- 内网不等于访问控制；公网发布需要独立安全配置。
- 数据处理边界以及哪些可选功能需要外网。

截图必须来自实际测试，去除 IP、账号、路径等敏感信息。不制作伪造平台安装截图。

## 提交流程

先完成规则核实、模板预检查、真实安装及更新测试，整理待提交材料。由维护者审核后再提交目录或 PR。不得自动向多个应用商店批量提交。

记录提交地址、日期、版本、审核反馈及后续维护责任。被拒绝时先判断产品/模板适配问题，不重复刷提交。

## 验收

在目标平台干净安装可运行；默认无多余权限；映射端口及 Web UI 正确；修改端口后仍正常；核心工具正常；升级及回滚测试通过；卸载没有意料外残留；项目和支持链接与实际入口一致。

## 分发效果与后续平台

关注安装反馈、有效支持问题、公开部署教程和引荐访问。模板收录、镜像拉取及独立用户分别记录。CasaOS 等候选只有在用户需求与测试环境具备后单独立项，不对未测试平台声明支持。

## 通用实施约束

1. 本文为需求与验收依据，不代表仓库已经具备文中能力。实施前检查实际代码、构建脚本、许可证、组件 API 和发布配置；不得虚构检查结果。
2. 产品名称统一为 JsonToolBox；官网为 https://jsontoolbox.cc/；主仓库为 https://github.com/kbmjj123/jsontoolbox.cc。新增包名、镜像名和仓库名均为待确认建议，发布前检查可用性。
3. 优先复用现有编辑器与处理逻辑，不复制维护第二套核心，不引入与需求无关的账号、数据库、云端处理和许可证验证服务。
4. JSON 内容不得默认上传、写入分析事件或附加在外部链接中；错误日志不得包含用户原文。不要把“本地处理”直接等同于整个页面没有外部请求。
5. 官网、源码和许可链接用于说明来源。不得要求强制反链、指定 dofollow、隐藏链接或堆砌关键词；品牌展示可关闭，不得影响功能。许可证义务以仓库实际许可证为准，不将保留网页反链描述为 MIT 的要求。
6. 新增追踪、外部服务、软件包发布、平台提交和对第三方发起 PR 均需维护者确认。默认不增加遥测。
7. 不为链接数量创建空壳包、重复仓库或无实际用途的适配层。下载、拉取、引用和真实用户分别统计，不混为一谈。
8. 使用项目现有包管理器、测试方案和编码规范；本文示例命名可按仓库结构调整，调整需说明理由。

## 开工前必须输出

- 相关文件、组件入口、构建命令及当前行为的检查记录。
- 已有能力、缺失能力和阻塞项列表；不能确认的内容标记“待核实”。
- 最小变更方案、拟修改文件清单及复用关系。
- 本次验收方式与回归范围。遇到架构或发布权限阻塞时停止猜测，记录需要维护者确认的决策。

## 交付与完成定义

- 可运行代码或配置、中文及英文使用说明、实际执行的测试结果、已知限制、回滚方式。
- 文档内命令必须在目标环境验证；未执行的测试标为“未验证”，不能直接勾选通过。
- 不影响官网现有工具、现有组件消费者及 Obsidian 插件；相关共享核心发生变更时执行回归。
- 发布前提供变更摘要、涉及外部服务清单和维护成本说明。未获得发布授权时仅交付待发布产物与操作说明。
