# 需求 05：真实文档项目接入与公开案例计划

## 优先级与目标

优先级：P1，在文档示例可运行后启动。本需求不是新增一个插件，而是验证现有组件能否解决真实项目的 JSON 展示问题，并在获得许可后整理案例。

不以外链数为成功标准；以第三方愿意保留集成、确有读者使用、维护成本可接受为判断依据。

## 候选项目要求

选择维护活跃、贡献规则清晰、公开文档确实含长 JSON 或复杂响应示例的项目。优先匹配已有 Vue/VitePress/Nuxt 集成能力。不因为域名指标高就选择无关项目。

首轮建议手工筛选 5—10 个候选，深入验证 2—3 个，不批量联系。数量为本次计划建议，不代表已有需求证据。

## 候选记录表

每个候选记录：项目、文档具体页面、现有问题证据、技术栈、预期改进、替代方案、贡献规则、联系渠道、维护负担及当前状态。公开记录不包含私人联系方式或未授权沟通原文。

## 演示与沟通流程

1. 阅读贡献指南和已有 Issue，避免重复提案。
2. 本地制作最小对比 demo：原有展示、组件展示及负载变化。
3. 先询问维护者是否希望尝试；若规则允许直接 PR，也应保持范围小且可撤销。
4. 明确说明自己是 JsonToolBox 维护者，解释本地处理与依赖，不夸大需求。
5. 不要求添加官网链接作为接受帮助的条件，不把推广链接混入无关修改。
6. 外部 Issue、评论、PR 和邮件经维护者确认后才发送；无回复不频繁催促。

## 集成质量要求

保留原有数据语义与文章内容；支持无 JS 降级、主题、移动端和可访问性。记录新增依赖、包体变化及维护方式。对方拒绝或移除时尊重选择，不尝试绕过决定。

## 案例制作

必须获得公开引用许可或仅引用已经公开允许使用的事实。案例包含原问题、方案、真实截图、限制、实现链接和可复现步骤。不编造使用量、推荐语或性能提升。

若对方愿意推荐，链接锚文本与位置由对方自主决定。本站可建立集成案例页，是否展示对方 Logo 需获得相应许可。

## 验收与评估窗口

首轮以约 4—8 周为评估窗口，记录实际反馈；这不是效果承诺。完成候选筛选、最小 demo、经批准的沟通、问题整理和是否继续投入的结论即可验收，不要求第三方必须合并。

出现无人愿意接入、集成成本过高或核心优势不清楚时，暂停扩展新平台，先改进示例和组件。禁止用更多空壳包替代需求验证。

## 交付物

候选评估表、可运行 demo、沟通草稿、反馈记录、可公开案例材料和下一轮决策。相关记录建议放维护目录，不全部作为面向搜索的公开页面发布。

## 通用实施约束

1. 本文为需求与验收依据，不代表仓库已经具备文中能力。实施前检查实际代码、构建脚本、许可证、组件 API 和发布配置；不得虚构检查结果。
2. 产品名称统一为 JsonToolBox；官网为 https://jsontoolbox.cc/；主仓库为 https://github.com/kbmjj123/jsontoolbox.cc。新增包名、镜像名和仓库名均为待确认建议，发布前检查可用性。
3. 优先复用现有编辑器与处理逻辑，不复制维护第二套核心，不引入与需求无关的账号、数据库、云端处理和许可证验证服务。
4. JSON 内容不得默认上传、写入分析事件或附加在外部链接中；错误日志不得包含用户原文。不要把“本地处理”直接等同于整个页面没有外部请求。
5. 官网、源码和许可链接用于说明来源。不得要求强制反链、指定 dofollow、隐藏链接或堆砌关键词；品牌展示可关闭，不得影响功能。许可证义务以仓库实际许可证为准，不将保留网页反链描述为 MIT 的要求。
6. 新增追踪、外部服务、软件包发布、平台提交和对第三方发起 PR 均需维护者确认。默认不增加遥测。
7. 不为链接数量创建空壳包、重复仓库或无实际用途的适配层。下载、拉取、引用和真实用户分别统计，不混为一谈。
8. 使用项目现有包管理器、测试方案和编码规范；本文示例命名可按仓库结构调整，调整需说明理由。

## 开工前必须输出

- 相关文件、组件入口、构建命令及当前行为的检查记录。
- 已有能力、缺失能力和阻塞项列表；不能确认的内容标记“待核实”。
- 最小变更方案、拟修改文件清单及复用关系。
- 本次验收方式与回归范围。遇到架构或发布权限阻塞时停止猜测，记录需要维护者确认的决策。

## 交付与完成定义

- 可运行代码或配置、中文及英文使用说明、实际执行的测试结果、已知限制、回滚方式。
- 文档内命令必须在目标环境验证；未执行的测试标为“未验证”，不能直接勾选通过。
- 不影响官网现有工具、现有组件消费者及 Obsidian 插件；相关共享核心发生变更时执行回归。
- 发布前提供变更摘要、涉及外部服务清单和维护成本说明。未获得发布授权时仅交付待发布产物与操作说明。
