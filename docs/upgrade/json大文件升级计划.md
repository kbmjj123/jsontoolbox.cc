实际的大文件功能，核心不是“把普通 JSON 编辑器做得更强”，而是围绕 **快速打开、搜索定位、局部查看、低内存占用** 设计。现有大型文件查看器通常提供虚拟滚动、后台索引、正则搜索、跳转行号、上下文查看和结果导出等能力。 [github](https://github.com/woanware/LogViewer)

## 第一阶段：必须有

这是最适合你优先实现的功能集合。

### 1. 大文件检测

用户选择文件后，先显示：

- 文件名。
- 文件大小。
- 文件类型。
- 编码检测结果。
- 是否可能是 JSON、NDJSON、CSV 或普通文本。
- 当前处理模式。
- 预计支持的功能。

例如：

> `large-data.json` · 86 MB  
> 大文件模式：支持搜索、定位、上下文查看和片段导出；不支持完整格式化和树形编辑。

这一步很重要，可以提前管理用户预期。

### 2. 快速打开

不要等待整个文件解析完成后才显示页面，应采用渐进式加载：

- 立即显示文件信息。
- 先读取文件头部。
- 先显示前几行或第一个片段。
- 后台启动索引或搜索任务。
- 显示当前进度。
- 允许用户在索引过程中取消。

“打开”不应等于“把整个文件解析成完整对象”。

### 3. 纯文本查看器

大文件模式应优先使用轻量文本查看器，而不是完整 JSON 编辑器。

建议支持：

- 只读查看。
- 当前片段滚动。
- 行号。
- 列号。
- 横向滚动。
- 超长行处理。
- 当前行高亮。
- 换行开关。
- 原始文本和格式化片段切换。

尤其要处理“单行极长”的情况。一个 10 MB、只有一行的 JSON，可能比一个包含几十万行的 50 MB 文件更容易造成界面卡顿。大型查看器通常提供长行截断、隐藏或特殊处理能力。 [giantjson](https://giantjson.com/)

### 4. 关键词搜索

这是大文件模式的核心功能，至少应包括：

- 普通文本搜索。
- 区分大小写。
- 不区分大小写。
- 区分完整单词。
- 搜索 key。
- 搜索 value。
- 搜索全部内容。
- 上一个匹配。
- 下一个匹配。
- 匹配数量。
- 搜索耗时。
- 搜索进度。
- 取消搜索。
- 搜索历史。

搜索结果不能一次性渲染几万条，必须使用分页或虚拟列表。大型 JSON 工具通常会把搜索范围区分为 key、value 和全部内容，并提供结果计数及匹配跳转。 [convertjson](https://www.convertjson.io/json-viewer)

### 5. 跳转到匹配位置

点击搜索结果后，应能定位到：

- 文件中的字符偏移。
- 行号。
- 列号。
- 匹配内容。
- 前后文。
- 当前匹配在全部结果中的位置。

例如：

```text
匹配 12 / 438
行 182,430，列 17
上下文：..."userId":"abc-123","status":"active"...
```

对用户来说，“找到”不够，必须能快速看到它在文件中的实际位置。

### 6. 上下文查看

不要只显示匹配字符串。建议提供：

- 匹配前 N 行。
- 当前匹配行。
- 匹配后 N 行。
- 前后字符数设置。
- 一键复制上下文。
- 一键导出当前结果。
- 展开或收起上下文。

这对日志、API 响应、数据库导出和埋点数据尤其有用。

## 第二阶段：JSON 专用能力

如果你的产品定位仍然是 JSON 工具，那么大文件模式可以逐步增加 JSON 相关能力。但这些功能不一定需要建立完整内存对象树。

### 1. JSON 结构识别

支持识别：

- Object。
- Array。
- String。
- Number。
- Boolean。
- Null。
- 嵌套层级。
- JSON 是否完整。
- 是否存在非法字符。

这里可以先做“结构扫描”，不一定马上 `JSON.parse()`。

### 2. JSONPath 显示

当用户定位到某个 JSON 节点时，显示它的路径，例如：

```text
$.users[18420].profile.email
```

还可以提供：

- 复制 JSONPath。
- 复制当前节点。
- 复制当前节点的父路径。
- 根据路径跳转。
- 输入路径定位节点。

JSONPath 是大型 JSON 查看器的常见能力，尤其适合用户明确知道字段路径、但不想在庞大树结构中手动展开的场景。 [hi-malay.github](https://hi-malay.github.io/bigjson/)

### 3. Key 和 Value 搜索

建议将搜索范围拆成：

| 搜索范围 | 使用场景 |
|---|---|
| 全部 | 不确定数据在哪里 |
| Key | 查找字段名的使用位置 |
| Value | 查找 ID、邮箱、状态、URL 等具体内容 |
| Path | 查找特定结构路径 |

例如，搜索 `email` 时，用户可能只想找字段名；搜索 `abc@example.com` 时，通常只想找值。

### 4. 节点局部预览

点击一个节点后，可以显示：

- 当前节点类型。
- 当前节点大小。
- 子节点数量。
- JSONPath。
- 原始文本。
- 简化后的格式化内容。
- 复制节点。
- 下载节点。

注意这里的“格式化”应当只针对当前局部节点，而不是重新格式化整个文件。

### 5. 数组跳转

对于大型数组，不能要求用户一直滚动。应支持：

- 跳转到数组下标。
- 显示数组长度。
- 首页、末页。
- 上一项、下一项。
- 每页显示数量。
- 按索引范围查看。

例如：

```text
当前数组：$.orders
总数：2,450,000
跳转到：184200
```

## 第三阶段：高级搜索

这些功能有价值，但不建议一开始全部实现。

### 1. 正则搜索

适合：

- 日志过滤。
- URL 查找。
- UUID 查找。
- 邮箱查找。
- 错误信息匹配。
- 多种格式字段定位。

必须提供：

- 正则开关。
- 正则错误提示。
- 搜索取消。
- 匹配上限。
- 超时保护。

不要允许复杂正则无限制运行，否则用户可以输入灾难性回溯表达式，造成 Worker 长时间占用。

### 2. 多关键词搜索

可以支持：

- 任意关键词匹配。
- 全部关键词匹配。
- 排除关键词。
- 布尔条件。
- 多词高亮。

例如：

```text
error AND timeout
warning OR failed
error NOT healthcheck
```

大型日志查看器通常会提供多条件搜索、累计搜索和正则模式。 [github](https://github.com/woanware/LogViewer)

### 3. JSONPath 查询

在普通搜索稳定之后，可以增加：

```text
$.users[*].email
$.orders[?(@.total > 1000)]
$..error
```

但需要客观区分：

- JSONPath 需要结构解析。
- 普通关键词搜索只需要文本扫描。
- 对超大文件执行完整 JSONPath 可能需要索引或流式解析。
- 不同 JSONPath 实现的语法并不完全一致。

因此，不建议一开始宣称“完整支持 JSONPath”。可以先支持有限子集：

- 根路径。
- 属性访问。
- 数组下标。
- 递归字段搜索。

### 4. jq 类查询

这是高级用户需要的功能，但浏览器端实现复杂度较高：

- 需要流式 JSON 解析。
- 需要处理错误。
- 需要限制执行时间。
- 需要展示查询结果。
- 需要支持结果导出。

可以后置，或者另做“JSON Query”工具，不必直接塞进大文件查看器。

## 第四阶段：结果处理

大文件工具不能只负责“看”，还要让用户处理搜索结果。

建议支持：

- 复制当前匹配。
- 复制当前行。
- 复制上下文。
- 导出所有匹配行。
- 导出为 TXT。
- 导出为 JSON。
- 导出为 CSV。
- 只导出匹配的 JSON 节点。
- 显示结果数量限制。
- 保存搜索条件。

例如，用户搜索：

```text
status = "failed"
```

然后可以导出所有命中的行，而不必重新处理整个文件。

大型文件工具通常会提供当前视图导出、匹配结果导出和上下文范围设置。 [github](https://github.com/woanware/LogViewer)

## 第五阶段：性能和可靠性功能

这部分是大文件模式与普通模式最重要的区别。

### 1. Web Worker

以下工作应尽可能放入 Worker：

- 分块读取后的文本扫描。
- 行号计算。
- 关键词搜索。
- 正则搜索。
- 编码转换。
- 简单结构识别。
- 结果索引。

主线程只做界面更新。

### 2. 搜索进度

搜索时显示：

```text
正在搜索：42%
已扫描：38 MB / 90 MB
已找到：1,284 个匹配
```

即使实际速度很快，进度也有助于用户理解当前状态。

### 3. 取消操作

必须支持取消：

- 取消当前搜索。
- 取消结构扫描。
- 取消导出。
- 关闭文件。
- 更换搜索词时取消旧任务。

如果用户输入新关键词，旧搜索任务不应继续占用资源。

### 4. 内存保护

建议限制：

- 最大显示结果数。
- 最大上下文长度。
- 最大单行显示长度。
- 最大正则运行时间。
- 最大导出结果量。
- 最大同时缓存的文件片段数量。

比起直接报错，更好的体验是提示：

> 文件已扫描完成，共找到 58,420 个匹配。当前仅显示前 500 条，可继续加载或导出全部结果。

### 5. 编码检测

大文件不一定都是 UTF-8。可以考虑支持：

- UTF-8。
- UTF-8 BOM。
- UTF-16 LE/BE。
- Windows-1252。
- GBK/GB18030。

不过浏览器原生对 GBK 等编码的支持有限，编码识别和解码需要单独设计。可以先支持 UTF-8、UTF-16，再根据真实用户需求扩展。

### 6. 错误恢复

需要明确处理：

- 文件读取失败。
- 文件被用户移除。
- 编码无法识别。
- 正则表达式错误。
- 搜索任务中断。
- 文件不是合法 JSON。
- JSON 截断。
- 浏览器内存不足。

不要因为文件不是合法 JSON 就无法使用搜索功能。即使 JSON 不完整，用户仍然可能只是想从里面查找字符串。

## 不建议优先做的功能

以下功能看起来很有吸引力，但不适合作为第一版大文件能力：

- 大文件实时编辑。
- 全文件格式化。
- 全文件压缩。
- 完整树形展开。
- 全文件 diff。
- 全文件 JSON Schema 校验。
- 完整 jq。
- 无限结果高亮。
- 一次性生成完整对象树。
- 依赖 Monaco 的全量编辑模型。

这些功能不是不能做，而是会显著增加内存、计算和交互复杂度。大文件工具优先解决“看、搜、跳、取”，而不是“改”。

## 推荐的最小版本

结合你的 JSON 工具定位，我建议大文件模式第一版只做这些：

1. 本地文件读取，不上传服务器。
2. 文件大小和类型检测。
3. Worker 分块搜索。
4. 普通文本搜索。
5. 大小写选项。
6. Key、Value、全部内容三种范围。
7. 搜索结果分页或虚拟列表。
8. 行号、列号和字符偏移。
9. 上下文查看。
10. 上一个/下一个匹配。
11. 跳转到行号或偏移。
12. 复制当前匹配和上下文。
13. 导出匹配结果。
14. 搜索取消和进度显示。
15. 超长行保护。
16. 文件完全留在浏览器本地。

## 适合你的产品定位

你可以将大文件功能定义为：

> A privacy-first large JSON and text file searcher for fast local inspection.

中文可以写成：

> 面向大型 JSON 和文本文件的本地搜索与定位工具，支持分块处理、上下文预览和结果导出。

这样的定位比“大文件 JSON 编辑器”更准确，也更容易在技术上兑现。因为当前最有价值、最可控的功能不是完整编辑，而是**快速找到数据，并让用户确认它位于哪里**。
