# 文案 ↔ 实现一致性铁律（Copy Accuracy）

> 适用范围：一切面向用户的文字——工具 JSON、组件内文案、i18n 文案、博客正文。
> 优先级：**阻断级**。文案承诺但没实现、实现与文案相反，等同于 bug，不允许带着上线。

---

## 0. 为什么单独立一条

逐页优化时发现的问题里，最多的一类**不是「没做功能」，而是「文案承诺了但没实现」或「实现与文案相反」**。
这类问题靠 code review 几乎看不出来：reviewer 读代码不会同时读落地页文案，读文案也不会去翻实现。
**只能靠「文案 → 实现」逐条机械核对**，因此本文件同时给出**能力清单（去哪找文案）**与**核对清单（怎么核）**。

---

## 1. 铁律（不可协商）

1. **可指认原则**：写进文案的每一条能力断言，都必须能在代码里指出 `文件:行号`。指不出来 → 删文案或补实现，二选一，不允许「先写文案，实现待补」留在仓库。
2. **方向一致**：数量（单文件 / 多文件）、顺序（输入顺序 / 升序）、范围（全量 / 前 N 项）、默认值、上限——文案与实现必须同向。写「按输入顺序」就不能实现成排序；写「支持多个」就不能只收一个。
3. **不承诺不做的事**：项目明确不做的（大文件编辑、全文件格式化、任意体积、服务端处理、GBK 输出等），文案一律不得暗示，除非实现真实存在。
4. **同步修改**：改实现 → 回扫文案；改文案 → 回扫实现。两者永远在同一个改动里落地，不允许拆成两次提交。
5. **语言键错误的严重性**：键名写错**不会报错，只会整块静默为空**。本项目有两套键名，**写反就是白屏级缺陷**：
   - `app/assets/data/**/*.json` → 顶层语言键是 **`en` / `zh`**
   - `i18n/locales/` → 文件名是 **`en.json` / `zh-CN.json`**（i18n 模块内部用 `zh-CN`）
6. **英文兜底会漏出**：`tool.ui?.label_input || 'Input JSON'` 这类兜底在英文站无感，在 zh 站会漏出英文。所有兜底要么中英两侧都提供该键，要么兜底串本身是语言无关的（图标、数字）。
7. **SEO 文案同样受约束**：`meta.title / meta.description / keywords` 与 `faq[]`（会生成 FAQPage 结构化数据）会被搜索引擎当成能力声明，承诺不实等于误导收录。

## 2. 能力清单（本项目所有文案载体）

核对时**逐项拉取**，不要凭印象：

| # | 载体 | 渲染位置 | 典型越权承诺 |
|---|------|---------|-------------|
| 1 | `{slug}.json` → `en/zh.features[]` | 落地页 Feature 区块 | 「支持 X」但组件无对应控件 |
| 2 | `{slug}.json` → `en/zh.guide[]` | How to use 步骤 | 描述了理想流程，实现里没有那一步 |
| 3 | `{slug}.json` → `en/zh.faq[]` | FAQ + FAQPage schema | 回答里承诺了能力上限/格式/编码 |
| 4 | `{slug}.json` → `en/zh.article` | 正文 SEO 内容 | **最危险**：长文最容易写成「应有功能」 |
| 5 | `{slug}.json` → `en/zh.meta.*` | title / description / keywords | 关键词堆砌出不存在的能力 |
| 6 | `{slug}.json` → `en/zh.hero.trustHtml` | Hero 信任条 | 「不上传 / 无限制 / 支持任意大小」 |
| 7 | `{slug}.json` → `en/zh.ui.*` | 按钮、标签、错误提示 | 文案有 key，组件没读或读错 key |
| 8 | `app/components/universal/*.vue` 内硬编码串 | 工具主体 | 只有英文、绕过 i18n、与 JSON 文案矛盾 |
| 9 | `app/components/tool/*` 共享组件默认文案 | 输入/输出面板等 | 默认值与工具实际行为不符 |
| 10 | `i18n/locales/*.json` | 全局文案 | key 拼错 → 静默显示 key 或空 |
| 11 | `content/{en,zh}/blog/*.md` + frontmatter | 博客 | 描述某工具能力时同样受本铁律约束 |
| 12 | `recommends` / `nextSteps` | 相关工具推荐 | 指向的工具不存在或能力不匹配 |

## 3. 核对清单（Copy ↔ Implementation Audit）

对每一个被改动/被优化的页面执行，**输出成表格留存**：

| 文案断言 | 来源（文件:行） | 实现位置（文件:行） | 结论 |
|---|---|---|---|

步骤：

1. **收集**：按第 2 节清单把该页 `en` + `zh` 两套文案全部取出（含组件硬编码串）。
2. **拆断言**：拆成原子能力声明——一句话一个断言（支持 X / 可 Y / 最多 N / 顺序为 Z / 不上传 / 默认 W）。
3. **找证据**：每条断言到组件 / composable / util 里找实现；找不到 → 判定「未实现」。
4. **核方向**：数量、顺序、范围、默认值、上限逐一比对（这是最容易反的地方）。
5. **核双语**：`en` 与 `zh` 的断言集合必须一一对应；zh 不得少功能，也不得多承诺。
6. **核键名**：语言键（`zh` vs `zh-CN`）、i18n key 拼写、`tool.ui` 的 key 与组件读取的 key。
7. **核兜底**：把每条 `?? '英文'` 兜底问一遍——zh 页面会不会漏出英文？
8. **反问测试**：把断言反着问「如果不支持会怎样」，确认实现不会**静默降级**（例如超限文件被悄悄截断、多文件只处理第一个）。
9. **记录**：未修正项必须显式列出，不允许「大概没问题」。

## 4. 本项目高频反例（照着自查）

| 反例 | 症状 |
|---|---|
| 文案写「支持大文件编辑」，实际普通页有 `LARGE_FILE_MAX_BYTES` 门槛 | 承诺与实现相反 |
| 文案写「按输入顺序处理」，实现里 `sort()` 成升序 | 方向相反 |
| 文案写「可选横向 / 纵向」，组件无该控件 | 未实现 |
| 文案写「一次处理多个」，实现只取 `files[0]` | 数量不符 |
| 语言键写成 `zh-CN`（应为 `zh`）或反之 | **整块静默为空**，不报错 |
| `tool.ui?.xxx \|\| 'English'` 兜底 | zh 页漏英文 |
| `article` 长文描述「自动修复 / 智能识别 / 批量」 | 最常被写成理想功能 |
| FAQ 回答给出具体体积上限，代码里没有对应常量 | 数字无出处 |
| `recommends` 指向不存在或不匹配的 slug | 死链 / 语义断裂 |

## 5. 强制执行时机

以下任一情况**必须**跑完第 3 节清单：

- 新增或重写工具页（JSON + 组件）
- 修改任一 tool JSON 的 `features` / `guide` / `faq` / `article` / `meta` / `hero` / `ui`
- 修改任一 `universal` 组件的可观测行为（按钮、上限、默认值、处理顺序）
- 修改共享组件（`app/components/tool/*`）的默认文案或兜底值
- 修 bug 时，若该 bug 影响用户可见行为 → 顺带核对相关承诺
- 任何「逐页优化 / SEO 优化」任务

---

## 6. 与其他规则的关系

- 文案**语气与术语**遵循 `i18n-translation-rules.md`，本文件只管**真值**，不管文风。
- 工具注册与字段结构遵循 `tool-system.md`。
- 落地页结构与 SEO 流程遵循 `seo-workflow.md` / `seo-i18n.md`。
- 冲突时：**本文件的「可指认原则」优先**——宁可文案少写，不可多承诺。
